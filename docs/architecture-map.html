architecture & delivery map

muis / how the whole thing fits together

A terminal emulator for Veldmuis: a Tauri 2 native window around an xterm.js frontend, a Rust shell that owns process lifecycle, and one muis-worker process per session that owns the PTYs. This page maps the runtime, the wire protocol, persistence, the UI module graph, all build and packaging paths, the test layers, and both GitHub Actions pipelines.

01 System in one picture

Two process types at runtime: the shell (one Tauri window) and one worker per session (a UI “session” is a workspace holding tabs). Each tab is a PTY inside its session's worker. The UI never owns a PTY, so a worker crash only takes down that one session.

The central invariant: one muis-worker process per session, one PTY per tab. The shell never parses terminal output; it only routes JSON lines. The frontend never owns a shell process. A crash is therefore contained to one session, and the rest of the window survives.

02 Component inventory

Where each responsibility lives, and what depends on what.

muis-core

UI-agnostic model & protocol

No Tauri, no PTY, no WebView. Defines the session/tab/workspace structs, the serializable IPC frames (both directions), platform paths, shell probing, and the local notification socket protocol. This is the crate that compiles and unit-tests anywhere, including CI without WebKit.

muis-worker

PTY owner

One process per session. Opens PTYs with portable-pty, spawns the shell, forwards base64 output, keeps a 256 KiB scrollback ring per PTY, handles resize/kill/snapshot, and exits when stdin reaches EOF so no orphan shells are left behind.

muis-shell

Tauri window & supervisor

The muis binary. Hosts the WebView, exposes Tauri commands, supervises WorkerPool, serves the notification socket, samples CPU/RAM/GPU, writes diagnostics, and owns config, session, and snapshot persistence. On Windows it also embeds the worker and notify CLIs behind hidden flags.

muis-notify

Notification CLI

Sends one JSON request to the running shell over the per-user local socket. Defaults --socket and --tab from MUIS_SOCKET and MUIS_TAB_ID, which are injected into every PTY. Exposed as a library so the Windows single-exe build can re-exec it.

03 Runtime model & Tauri surface

The shell process is the only bridge between the WebView and the OS. The frontend calls commands; the shell emits events back. Worker traffic is JSON lines, not Tauri events, until it reaches WorkerPool.

Process model

  • muis shell — one process, one window, one WorkerPool.
  • muis-worker — one per session (workspace ID), idempotent spawn.
  • PTY — one per tab; the worker holds the master, the shell is the child.
  • Real shell / agent — child of the PTY; can die without killing muis.
  • muis-notify — short-lived client; connects to the shell's local socket.

Why one worker per session?

Process isolation is the crash boundary. A panic, OOM, or segfault in a worker affects only that session's PTYs. Stdin EOF from the shell means the UI is gone, so the worker kills its children and exits; no orphan shells. The shell stays responsive and other sessions keep their PTYs.

04 The UI ↔ worker wire protocol

JSON Lines over the worker's stdin/stdout. Bytes are base64 because terminal input and output are not guaranteed UTF-8. The Rust and TypeScript definitions are kept in lockstep by a shared fixture that both test suites parse.

Example frames

{"type":"spawn","pty_id":"t1","shell":"/usr/bin/fish",
 "cwd":"/home/user","cols":80,"rows":24}

{"type":"write","pty_id":"t1","data_b64":"bHMgLWxhCg=="}

{"type":"spawned","pty_id":"t1"}

{"type":"output","pty_id":"t1","data_b64":"aGVsbG8tbXVpcwo="}

{"type":"exited","pty_id":"t1","code":0}
Contract lock: tests/fixtures/ipc-frames.jsonl contains all ten frames. muis-core decodes/re-encodes every line, and the TypeScript ipc.test.ts parses the same file. If either side renames a tag or field, both test suites fail.
Worker death signal: the pool emits { "type":"error", "pty_id":"", "message":"worker process ended" } when a worker's stdout reaches EOF. The UI treats that as “every tab in this session lost its PTY”. The current WorkerClient has onWorkerDead/isSessionDead; the reconnect UX is still a future hook rather than a visible flow.

05 Startup, input, output, restore

The first few hundred milliseconds decide whether the window shows real terminals or a blank frame. The sequence below is the production path on a normal Tauri launch.

06 Frontend structure

main.ts is deliberately a hub; everything interesting is a pure, unit-testable module beside it. The DOM is built imperatively to match the Breeze target, not through a framework.

Window regions

Titlebar

Frameless drag region, app icon/title, search box (cross-session search, regex/case, history), window controls, test-mode badge.

Sessions sidebar

One tile per workspace with color/glyph, tab count, cwd, done badge, reorder drag, context menu, new-session dialog with folder picker and subfolder quick picks.

Tabbar

One tab per PTY, active state, done state, last-command label, close/middle-click, reorder, drag into another session, new-tab and settings buttons.

Terminal column

One xterm surface per tab, a last-command head, WebGL with canvas fallback, FitAddon, SearchAddon, OSC 8 links, bell modes, clipboard modes.

Statusbar

cwd, git branch, session·tab, user@host, CPU/RAM/GPU, shell, version, clock. Every segment is individually toggleable.

Overlays / slots

Settings dialog, command palette, session dialog, context menu, search results, and a reserved right-side panel slot (no panel registered yet).

Terminal intelligence pipelines

Title precedence: a manually pinned tab title always wins. Otherwise muis shows a meaningful shell title (e.g. opencode naming its session) and falls back to the last command. Fish's abbreviated cwd and auto “Terminal N” placeholders are not shown as titles.

07 State, persistence & restore

The shell owns every file. The frontend sends raw JSON; the shell validates it before writing so a UI bug cannot corrupt the session store.

State locations

Session JSON

{
  "workspaces": [
    {
      "id": "w1",
      "name": "home",
      "dir": "/home/user",
      "active": 0,
      "tabs": [
        { "id": "t1", "title": "Terminal 1",
          "cwd": "/home/user", "manual": false }
      ]
    }
  ],
  "current": 0,
  "next_id": 2
}

Rules

  • IDs are never reused. next_id survives restore and is clamped past every ID found in the file.
  • Closing the last tab keeps the session. The workspace survives with zero tabs and shows only the + button.
  • Process exit removes the session when it was the last tab's PTY; manual close does not.
  • Restored tabs replay once from their own scrollback file; the tab id is the join key.
  • Snapshots are periodic every 30 s for every tab with a live view, plus removal on close.

08 Build pipeline

Two independent builds meet at the Tauri shell: the Vite frontend becomes src-ui/dist, the Rust workspace becomes binaries, and muis-shell embeds the dist at compile time.

Local commands

# Rust workspace
cargo build
cargo test --workspace --locked

# Frontend
cd src-ui
npm ci
npm test          # vitest
npm run build     # tsc --noEmit && vite build

# Dev window (needs system WebKit)
cargo run -p muis-shell
# Native PTY smoke
npm ci --prefix src-ui
npm run build --prefix src-ui
cargo build --locked \
  -p muis-shell -p muis-worker -p muis-notify
npm ci --prefix tests/e2e
npm run test:live:x11 --prefix tests/e2e

# AppImage (manual)
(cd crates/muis-shell && \
  ../../src-ui/node_modules/.bin/tauri build --bundles appimage)
Why the Tauri shell is the merge point: tauri.conf.json points frontendDist at ../../src-ui/dist and tauri-build generates the context that embeds it. If the UI was not built first, the shell build embeds an old or missing dist.

Platform-specific shell spawning

Linux native

$SHELL if executable, else fish → bash → sh. Fish gets -C init snippets: silence the greeting and emit OSC 133 C/D markers. TERM=xterm-256color, LANG=C.UTF-8, TERM_PROGRAM=muis, MUIS_TAB_ID.

Windows

Probe pwsh.exe → powershell.exe → cmd.exe, then %SystemRoot%\System32\cmd.exe. The worker runs inside the same exe via re-exec. CREATE_NO_WINDOW prevents console flashes.

Flatpak

flatpak-spawn --host --directory=<cwd> --env=KEY=VALUE … shell. Only explicitly forwarded variables cross the sandbox boundary; the user gets their real host shell and tools.

Release signing key

Public material lives in packaging/keys/: muis-release.gpg (binary keyring for gpgv), muis-release.asc (armored public key), muis-trusted (pinned primary fingerprint), and a README covering verification and rotation. The private material never lives in the repo; the signing subkey and passphrase are provided to the protected release GitHub Environment as secrets.

13 GitHub flow end to end

How a change travels from a local branch to a signed release, and which automation sees it at each step.

Review checklist implied by the repo

  • Branch from main in an isolated worktree; keep main read-only.
  • Run cargo test --workspace --locked and the UI tests/build.
  • For terminal/session changes, run the native Xvfb smoke.
  • Verify there is exactly one visible terminal across session/tab switches.
  • Check docs and version authorities when the change affects packaging.

What the maintainer must do for a release

  • Bump crates/muis-shell/tauri.conf.json.
  • Tag v<version> on main and push the tag.
  • Let release.yml build, sign, verify, and publish.
  • Bump aur/PKGBUILD and refresh .SRCINFO separately.
  • Optionally update the Veldmuis package that repackages the release.

14 Notable implementation details & drift

Things worth knowing before changing the code or trusting the docs.

Invariants worth preserving

  • Session ID = workspace ID. WorkerPool is keyed by it; tabs are pty_ids inside that worker.
  • Worker spawn is idempotent. Selecting a tab again does not start a second worker.
  • Snapshot ids are sanitized. A crafted tab id cannot escape the sessions directory.
  • Config/session writes validate JSON before touching disk.
  • Test mode never writes real sessions, config, or snapshots.
  • Windows never spawns the downloaded exe directly as the worker; it stages a MOTW-free copy first.

Known drift / stale docs

  • Version sources disagree: tauri.conf.json is 1.4.0; crates and src-ui/package.json are 0.1.0/1.0.0; aur/PKGBUILD is 1.0.0.
  • README still describes a three-exe Windows zip; the current code and release build a single muis.exe.
  • Planning docs mention ACP/agent code that is not in this tree. crates/muis-shell/src/ contains only bridge, logging, main, and persist.
  • muis-core session/config structs are not wired into the live shell; the TS store is authoritative for the running app, while the Rust types are exercised by unit tests.
  • Worker reconnect is a hook, not a UX. onWorkerDead exists but no caller surfaces it yet.
  • Cross-session search scans open tabs' xterm buffers; there is no historical index once a tab is closed.
  • Flatpak deliberately omits muis-notify, because the sandbox socket cannot be reached from the host shell.

Bottom line: muis is a small Rust supervisor around a large xterm.js frontend, with a deliberately narrow JSON-lines boundary. The system is easy to reason about because the process model, the protocol, and the persistence format are all explicit and independently tested. The risk areas are the platform-specific packaging shims (Flatpak host spawn, AppImage env sanitization, Windows MOTW staging) and documentation drift between the code, planning docs, and version files.
